# Campaign Core Schema (Draft)

This is the implementation specification for TKT-0003. PostgreSQL is the canonical store; source files, transcripts, exports, and indexes are evidence or derived artifacts.

## Conventions

- All primary keys are UUIDs generated by Campaign Core.
- Canonical tables have `created_at` and `updated_at` timestamps; source records are immutable.
- Truth/workflow enumerations remain PostgreSQL types. Extensible record and family kinds use stable `kind_definitions` plus immutable `kind_versions`; registry metadata does not execute validation or exporter behavior.
- Every canonical write is performed only by `apply_change_set(change_set_id, reviewed_version, approval_id, reviewed_content_hash)` in one transaction.

## Source and identity

| Table | Required columns | Constraints |
| --- | --- | --- |
| `source_documents` | `id`, `source_kind`, `original_path`, `external_id`, `first_seen_at` | One source identity per connector/path or external ID; source absence cannot delete other rows. |
| `source_revisions` | `id`, `source_document_id`, `content_hash`, `raw_content`, `source_time`, `importer_version`, `captured_at` | Immutable; unique `(source_document_id, content_hash)`. |
| `source_extractions` | `source_revision_id`, `parser_version`, `import_run_id`, `extracted_at` | Append-only parser ledger; unique `(source_revision_id, parser_version)` makes unchanged-byte re-extraction idempotent without rewriting the source revision. |
| `kind_definitions` | `id`, `namespace`, `canonical_key`, `status`, `replacement_kind_id` | Stable identity for namespaced kinds; no arbitrary `other` fallback. |
| `kind_versions` | `kind_id`, `version`, documentation and behavior-version fields | Immutable reviewed coordinates retained by proposals and receipts. |
| `kind_aliases` | `namespace`, `alias_key`, `kind_id` | Rename keeps old machine keys resolvable without changing kind identity. |
| `records` | `id`, `record_type_kind_id`, `created_by_change_set_id`, `created_at` | Thin common identity only; family payloads do not become generic JSON. |
| `entities` | `id`, `entity_type`, `entity_kind_id`, `canonical_name`, `created_by_change_set_id` | `id` is also a `records.id`; new writes resolve `entity_type` only as the compatibility copy of an active controlled kind key. |
| `entity_aliases` | `id`, `entity_id`, `alias`, `alias_kind`, `source_revision_id` | Unique normalized alias only within a declared resolution namespace; similar aliases never merge entities automatically. |
| `source_spans` | `id`, `source_revision_id`, `section_path`, `start_offset`, `end_offset`, `excerpt_hash` | Immutable citation target for claims, relationships, and receipts. |
| `source_document_paths` | `source_document_id`, `connector`, `normalized_path`, `first_seen_at`, `last_seen_at`, `is_current`, `missing_scans` | Retains move history and missing-source confirmation without mutating the immutable original source identity. |

`source_documents` tracks moves through a new revision or reviewed identity match. A missing discovered path creates an import-review item; it never cascades to canonical deletion.

The initial controlled entity keys are `npc`, `pc`, `location`, `faction`, `item`, `event`, `worldbuilding`, and `rules_element`. Migration 0006 backfills matching values. An existing value outside this set keeps its stable entity and evidence, receives no guessed kind ID, and opens `unsupported_legacy_entity_kind` review. New writes fail closed unless the key resolves to an active entity-kind definition.

## Campaign records

| Table | Required columns | Constraints |
| --- | --- | --- |
| `workflow_sessions` | `id`, `kind`, `started_at`, `closed_at`, `parent_session_id` | Nested direct-lore operations reference their Brainstorm parent. |
| `brainstorm_sessions` | `workflow_session_id`, `title`, `idempotency_key` | One durable Brainstorm identity extends a `workflow_sessions` row; at most one open session is resumed by the workspace. |
| `brainstorm_thoughts` | `id`, `workflow_session_id`, `sequence`, source/revision/candidate IDs, verbatim `thought_text`, stable `mentions_json`, grounded `evidence_json`, `captured_at` | Append-only thoughts remain non-canonical evidence. Each thought preserves its direct-input provenance, entity-resolved mentions, and the continuity panel snapshot returned at capture time. |
| `brainstorm_pins` | `workflow_session_id`, `entity_id`, `position`, `pinned_at` | Ordered, session-scoped reference records kept visible in the Brainstorm continuity panel. Pins guide retrieval context but do not create or alter canonical claims. |
| `claims` | `id`, optional `subject_entity_id`, optional `predicate`, optional `object_entity_id`, primary `assertion_text`, `state`, `authority`, `confidence`, `visibility`, `recorded_at` (audit `timestamptz`), `effective_from_year/month/day`, `effective_until_year/month/day`, `expected_year/month/day`, `observed_year/month/day`, `campaign_calendar_id`, `session_id` | `assertion_text` and provenance preserve complete meaning. Subject/predicate/object are optional retrieval enrichment and do not gate promotion. Audit time is UTC; campaign chronology is integer-year under a `calendar_id` (ADR-0007). |
| `claim_evidence` | `claim_id`, `source_span_id`, `evidence_role` | Immutable provenance edge; no claim without at least one source span or a direct-input source revision. |
| `claim_supersessions` | `superseding_claim_id`, `superseded_claim_id`, `resolution_change_set_id`, `reason` | Pair is unique; a `superseded` state requires this edge. |
| `relationships` | `id`, `from_entity_id`, `to_entity_id`, `relationship_type`, `assertion_text`, plus the claim lifecycle/time columns | Subject to the same authority and evidence rules as claims. |
| `relationship_evidence` | `relationship_id`, `source_span_id`, `evidence_role` | Immutable provenance edge. |
| `review_items` | `id`, `kind`, `status`, `subject_type`, `subject_id`, `details`, `opened_by_change_set_id`, `resolved_by_change_set_id` | Used for retcons, identity ambiguity, missing sources, and failed intentions. |
| `tags` | `id`, `name`, `normalized_name`, `created_by_change_set_id` | Stable case-insensitive identity; optional organizational vocabulary. |
| `entity_tag_assignments` | `id`, `entity_id`, `tag_id`, assignment/removal change-set coordinates and times | At most one active assignment per entity/tag; removal is retained rather than deleting history. |
| `plans` | `id`, `plan_kind_id`, descriptive fields, lifecycle, knowledge boundary, visibility, owner/attribution, change-set coordinates | `id` is also a `records.id`; kind-specific ownership and player-knowledge boundaries are enforced by a trigger. |
| `plan_evidence` | `plan_id`, `source_span_id`, `evidence_role` | Multiple documents can support one stable named plan. |
| `plan_relationships` | `plan_id`, `related_plan_id`, `relationship_kind`, change-set coordinates | Real plan foreign keys; self-reference is rejected. |
| `plan_lifecycle_events` | `plan_id`, from/to lifecycle, change-set and time | Immutable, receipted lifecycle history. |
| `plan_lifecycle_evidence` | `lifecycle_event_id`, `claim_id` | Completed/failed transitions cite separate observed claims rather than creating outcome truth. |
| `campaign_session_runs` | `run_id`, `status`, real-world `session_date`, optional campaign date, `title`, capture linkage, timestamps | At most one open mutable live-play run exists. Closing links it to the immutable direct-input source document and capture identity. |
| `campaign_session_run_notes` | `note_id`, `run_id`, source/encounter/section context, `note_text`, `captured_at`, `updated_at` | Mutable scratch notes are ordered by capture time and cascade only with their non-canonical run; they never create claims directly. |

`claims` has check constraints requiring `observed_year` for `observed`, effective-range ordering (`effective_until_year >= effective_from_year`), and `object_entity_id <> subject_entity_id` when both are present. A database trigger rejects a claim that represents a future PC action or intent; PC campaign directions must be DM-only `prepared` or `possible` claims with conditional planning semantics. Campaign chronology is integer-year storage under a hardcoded `calendar_id` backed by the `campaign_calendars` spec (ADR-0007); a SQL function `campaign_day_ordinal` enables deterministic same-calendar day arithmetic, while unrelated calendars are never silently ordered.

The live session workspace is deliberately mutable and non-canonical. Table notes retain stable encounter context while the UI presents one chronological timeline. Session wrap-up passes the assembled text through the existing direct-input capture boundary; only that immutable source evidence and its separately reviewed claims become campaign truth.

## Proposals, approvals, and receipts

| Table | Required columns | Constraints |
| --- | --- | --- |
| `proposals` | `id`, `workflow_session_id`, `status`, `created_at`, `closed_at` | Logical proposal identity; one active version at a time. |
| `proposal_versions` | `id`, `proposal_id`, `version_number`, `content_hash`, `created_at`, `supersedes_version_id` | Immutable; unique `(proposal_id, version_number)`. Editing creates a new row. |
| `proposal_items` | `id`, `proposal_version_id`, `sequence`, `mutation_kind`, `target_type`, `target_id`, `before_json`, `after_json` | Immutable exact mutation set; unique `(proposal_version_id, sequence)`. |
| `proposal_candidate_bindings` | `proposal_item_id`, `candidate_id`, `source_revision_id`, `source_span_id`, `candidate_fingerprint`, `created_at` | Immutable one-to-one evidence and candidate coordinates for an import proposal item. |
| `approvals` | `id`, `proposal_version_id`, `scope_json`, `approved_at`, `revoked_at` | Scope contains explicit proposal-item IDs; approval cannot reference another version. |
| `change_sets` | `id`, `idempotency_key`, `workflow_session_id`, `proposal_version_id`, `approval_id`, `status`, `requested_at`, `applied_at` | Unique idempotency key and non-null approval binding; one change set per approved scope/version. |
| `change_set_items` | `id`, `change_set_id`, `proposal_item_id`, `outcome`, `before_json`, `after_json` | Captures exact applied result. |
| `receipts` | `id`, `change_set_id`, `input_source_revision_id`, `decision_json`, `conflict_json`, `outcome`, `issued_at` | Unique `change_set_id`; written in the same transaction as the mutation. |

The applying function locks the change set, proposal, proposal version, approval, proposal items, and mutation target identities; validates the latest reviewed version, approval scope, and content hash; applies all items; writes the receipt; and marks the change set applied. A failure rolls back every mutation and receipt. A retry with the same exact coordinates returns the prior receipt even if the proposal later gains another version.

The implemented canonical mutation kinds are `create_entity`, evidence-backed `create_claim`, separately dispatched `update_entity_metadata`, `create_plan`, and `transition_plan`. Unknown or mixed mutation families fail closed and roll back the transaction. `update_entity_metadata` verifies the complete current kind/version/tag snapshot against immutable `before_json`, preserves the entity/record UUID and canonical name, applies kind and active-tag history atomically, and writes the ordinary change-set receipt. Plan creation and lifecycle transitions use the same exact approval and sole `/change-sets/{change_set_id}/apply` boundary; completed or failed transitions require separate observed claims.

Candidate proposal construction is a non-canonical Campaign Core transaction. It verifies the selected revision belongs to the candidate, creates an immutable exact source span, validates explicit entity identities and claim dimensions, and stores the complete mutation version and hash. It rejects evidence-only, removed, quarantined, template, navigation, ambiguous-identity, conflicting, invalid-time, and PC-agency-violating inputs before approval exists. Editing adds a new immutable version and revokes unapplied approvals of older versions.

Entity proposal items display and hash `record_type`, `entity_kind`, `entity_kind_version`, and the full normalized tag list. The legacy `entity_type` JSON key is retained temporarily as an application-function compatibility coordinate and must equal `entity_kind`; it is not a free-text input. Tag assignment occurs inside the same applying transaction and receipt scope as entity creation.

Post-creation reclassification and tag replacement use `/entities/{entity_id}/metadata-proposals`, the matching exact-version approval endpoint, and the same sole canonical `/change-sets/{change_set_id}/apply` operation. Metadata proposals cannot rename an entity, cannot convert an established PC or NPC agency kind, and fail stale if any current kind or tag changed after proposal construction. `kind_evolution_events` and `kind_evolution_members` record reviewed add, rename, deprecate, replace, merge, and split migration topology; executable validation and storage changes still ship as code and forward migrations.

## Derived artifacts and imports

| Table | Required columns | Constraints |
| --- | --- | --- |
| `derived_artifacts` | `id`, `kind`, `format_version`, `content_hash`, `location`, `created_at`, `producer_version`, `export_profile_kind_id` | No foreign key path from this table authorizes direct claim mutation. |
| `artifact_inputs` | `artifact_id`, `claim_id`, `relationship_id`, `source_revision_id`, `entity_id` | Records authoritative inputs and permits rebuilds. Exactly one input is non-null. |
| `import_runs` | `id`, `connector`, `started_at`, `finished_at`, `importer_version`, `status`, `receipt_json` | Detailed, idempotent import receipt. |
| `import_observations` | `id`, `import_run_id`, `source_document_id`, `source_revision_id`, `classification`, `outcome`, `warning_json` | Supports quarantine, move candidates, and deletion review without canonical deletion. |
| `import_candidates` | `id`, `source_document_id`, `fingerprint`, assertion/state/authority/visibility fields, `status`, `review_status`, `extractor_version`, `first_seen_import_run_id` | Source lifecycle and human review disposition are separate; candidates remain non-canonical until scoped application. |
| `import_candidate_evidence` | `candidate_id`, `source_revision_id`, `section_path`, offsets | Links retained candidates to every supporting immutable revision without duplication. |
| `candidate_dispositions` | `id`, `candidate_id`, `disposition`, `reason`, `created_at` | Immutable reject/defer history; no foreign-key path authorizes canonical mutation. |
| `candidate_extraction_runs` | `id`, `candidate_id`, `extractor_version`, `segments_json`, `coverage_json`, `created_at` | Immutable append-only extraction attempt; numbered source clauses and their explicit dispositions are retained even when a run contains zero claims. |
| `candidate_extraction_failures` | `id`, `failure_group_id`, `candidate_id`, `attempt_number`, `error`, `raw_response`, extractor/model/prompt identifiers, `created_at` | Immutable derived diagnostics for rejected provider attempts; never canonical truth or proposal input. |
| `candidate_extractions` | `id`, `candidate_id`, `extraction_run_id`, `source_segment_ids`, extracted claim dimensions, confidence, provenance, `created_at` | Immutable non-canonical AI output grouped by run; every claim cites one or more deterministic source segments and re-extraction never updates or deletes prior rows. |
| `rules_element_mechanics` | `entity_id`, `rules_kind`, `summary`, `mechanics_jsonb`, `created_by_change_set_id` | Kind-specific structured mechanics for a `rules_element` entity; validated by code against `rules_kind` (`spell`/`feat`/`ability`). |

The Markdown import operation writes source evidence, candidates, review items, observations, and its receipt in one Campaign Core transaction. It has no path to `entities`, `claims`, or `relationships`. Promoting a reviewed candidate requires the separately versioned `apply_change_set` operation.

A rules-element entity carries structured mechanics in `rules_element_mechanics`, persisted by a change-set trigger when the entity is applied. A versioned Markdown-card export profile (`markdown-card/1`, registered under the `export_profile` namespace) renders an approved canonical rules element into a deterministic `rules_card` derived artifact. The export never mutates canonical records; regeneration under the same profile version is idempotent on content hash. The deprecated `other` artifact kind is retained for historical receipts but cannot be used for new artifacts.

The import-review read model queries these tables through Campaign Core only. Candidate detail slices the stored immutable UTF-8 revision using the recorded evidence offsets and returns that exact excerpt with path, section, classification, and hash. Receipt and review-item resources require DM visibility; candidate queries apply requester visibility in SQL. Pagination order is stable, and no read endpoint updates `review_items`, `import_candidates`, or canonical tables.

Candidate AI re-extraction appends a `candidate_extraction_runs` row and its zero or more `candidate_extractions`. The provider identifies atomic statements, cites source segment IDs, and proposes subject-predicate-object structure. Campaign Core copies exact evidence from source offsets, assigns source-owned truth dimensions, and derives reciprocal coverage and claim indexes deterministically. Review reads select only the latest run, while all earlier runs and claim rows remain retained for audit.

If all bounded attempts fail, no extraction run or claim is created. Each rejected attempt is instead retained in `candidate_extraction_failures` with its validation error, raw response when one existed, and the effective extractor/model/prompt provenance. A later attempt receives the preceding validation error as corrective context.

When `apply_change_set` commits, a transaction-bound trigger reconciles linked candidates only after all items for that candidate in the reviewed version have been applied. Multiple explicitly scoped approvals may complete one version without promoting siblings early. The same trigger closes the proposal only when every version item has an applied change-set item.

## Migration and rollback

Each migration is forward-only, transactional, and records its version in `campaign_schema_migrations`. Destructive column or enum changes use expand/backfill/contract migrations: first add compatible structures, backfill in a separately resumable job, deploy readers/writers that understand both forms, then remove the old form in a later release. Rollback before a destructive contract is the previous application plus its compatible schema; after one, restore the last tested logical PostgreSQL backup into a new database and cut over only after validation. Campaign truth is never rolled back by deleting source evidence or receipts.
