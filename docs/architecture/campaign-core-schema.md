# Campaign Core Schema (Draft)

This is the implementation specification for TKT-0003. PostgreSQL is the canonical store; source files, transcripts, exports, and indexes are evidence or derived artifacts.

## Conventions

- All primary keys are UUIDs generated by Campaign Core.
- Canonical tables have `created_at` and `updated_at` timestamps; source records are immutable.
- Enumerations are PostgreSQL types: `claim_state`, `authority_kind`, `workflow_kind`, `proposal_status`, `change_set_status`, and `artifact_kind`.
- Every canonical write is performed only by `apply_change_set(change_set_id, reviewed_version, approval_id, reviewed_content_hash)` in one transaction.

## Source and identity

| Table | Required columns | Constraints |
| --- | --- | --- |
| `source_documents` | `id`, `source_kind`, `original_path`, `external_id`, `first_seen_at` | One source identity per connector/path or external ID; source absence cannot delete other rows. |
| `source_revisions` | `id`, `source_document_id`, `content_hash`, `raw_content`, `source_time`, `importer_version`, `captured_at` | Immutable; unique `(source_document_id, content_hash)`. |
| `source_extractions` | `source_revision_id`, `parser_version`, `import_run_id`, `extracted_at` | Append-only parser ledger; unique `(source_revision_id, parser_version)` makes unchanged-byte re-extraction idempotent without rewriting the source revision. |
| `entities` | `id`, `entity_type`, `canonical_name`, `created_by_change_set_id` | IDs never derive from a path or name. |
| `entity_aliases` | `id`, `entity_id`, `alias`, `alias_kind`, `source_revision_id` | Unique normalized alias only within a declared resolution namespace; similar aliases never merge entities automatically. |
| `source_spans` | `id`, `source_revision_id`, `section_path`, `start_offset`, `end_offset`, `excerpt_hash` | Immutable citation target for claims, relationships, and receipts. |
| `source_document_paths` | `source_document_id`, `connector`, `normalized_path`, `first_seen_at`, `last_seen_at`, `is_current`, `missing_scans` | Retains move history and missing-source confirmation without mutating the immutable original source identity. |

`source_documents` tracks moves through a new revision or reviewed identity match. A missing discovered path creates an import-review item; it never cascades to canonical deletion.

## Campaign records

| Table | Required columns | Constraints |
| --- | --- | --- |
| `workflow_sessions` | `id`, `kind`, `started_at`, `closed_at`, `parent_session_id` | Nested direct-lore operations reference their Brainstorm parent. |
| `claims` | `id`, `subject_entity_id`, `predicate`, `object_entity_id`, `assertion_text`, `state`, `authority`, `confidence`, `visibility`, `recorded_at`, `effective_from`, `effective_until`, `expected_at`, `observed_at`, `time_precision`, `session_id` | State, authority, time, and visibility are independent; `object_entity_id` is optional so prose is preserved. |
| `claim_evidence` | `claim_id`, `source_span_id`, `evidence_role` | Immutable provenance edge; no claim without at least one source span or a direct-input source revision. |
| `claim_supersessions` | `superseding_claim_id`, `superseded_claim_id`, `resolution_change_set_id`, `reason` | Pair is unique; a `superseded` state requires this edge. |
| `relationships` | `id`, `from_entity_id`, `to_entity_id`, `relationship_type`, `assertion_text`, plus the claim lifecycle/time columns | Subject to the same authority and evidence rules as claims. |
| `relationship_evidence` | `relationship_id`, `source_span_id`, `evidence_role` | Immutable provenance edge. |
| `review_items` | `id`, `kind`, `status`, `subject_type`, `subject_id`, `details`, `opened_by_change_set_id`, `resolved_by_change_set_id` | Used for retcons, identity ambiguity, missing sources, and failed intentions. |

`claims` has check constraints requiring `observed_at` for `observed`, `expected_at` for future-dated intended/prepared claims when a target is known, and `object_entity_id <> subject_entity_id` when both are present. A database trigger rejects a claim that represents a future PC action or intent; PC campaign directions must be DM-only `prepared` or `possible` claims with conditional planning semantics.

## Proposals, approvals, and receipts

| Table | Required columns | Constraints |
| --- | --- | --- |
| `proposals` | `id`, `workflow_session_id`, `status`, `created_at`, `closed_at` | Logical proposal identity; one active version at a time. |
| `proposal_versions` | `id`, `proposal_id`, `version_number`, `content_hash`, `created_at`, `supersedes_version_id` | Immutable; unique `(proposal_id, version_number)`. Editing creates a new row. |
| `proposal_items` | `id`, `proposal_version_id`, `sequence`, `mutation_kind`, `target_type`, `target_id`, `before_json`, `after_json` | Immutable exact mutation set; unique `(proposal_version_id, sequence)`. |
| `proposal_candidate_bindings` | `proposal_item_id`, `candidate_id`, `source_revision_id`, `source_span_id`, `candidate_fingerprint`, `created_at` | Immutable one-to-one evidence and candidate coordinates for an import proposal item. |
| `approvals` | `id`, `proposal_version_id`, `scope_json`, `approved_at`, `revoked_at` | Scope contains explicit proposal-item IDs; approval cannot reference another version. |
| `change_sets` | `id`, `idempotency_key`, `workflow_session_id`, `proposal_version_id`, `approval_id`, `status`, `requested_at`, `applied_at` | Unique idempotency key and non-null approval binding; one change set per approved scope/version. |
| `change_set_items` | `id`, `change_set_id`, `proposal_item_id`, `outcome`, `before_json`, `after_json` | Captures exact applied result. |
| `receipts` | `id`, `change_set_id`, `input_source_revision_id`, `decision_json`, `conflict_json`, `outcome`, `issued_at` | Unique `change_set_id`; written in the same transaction as the mutation. |

The applying function locks the change set, proposal, proposal version, approval, proposal items, and mutation target identities; validates the latest reviewed version, approval scope, and content hash; applies all items; writes the receipt; and marks the change set applied. A failure rolls back every mutation and receipt. A retry with the same exact coordinates returns the prior receipt even if the proposal later gains another version.

The first implemented mutation kinds are `create_entity` and evidence-backed `create_claim`. Unknown mutation kinds fail closed and roll back the transaction. Later mutation kinds extend this allowlist inside the same function; they do not add table-specific mutation endpoints.

Candidate proposal construction is a non-canonical Campaign Core transaction. It verifies the selected revision belongs to the candidate, creates an immutable exact source span, validates explicit entity identities and claim dimensions, and stores the complete mutation version and hash. It rejects evidence-only, removed, quarantined, template, navigation, ambiguous-identity, conflicting, invalid-time, and PC-agency-violating inputs before approval exists. Editing adds a new immutable version and revokes unapplied approvals of older versions.

## Derived artifacts and imports

| Table | Required columns | Constraints |
| --- | --- | --- |
| `derived_artifacts` | `id`, `kind`, `format_version`, `content_hash`, `location`, `created_at`, `producer_version` | No foreign key path from this table authorizes direct claim mutation. |
| `artifact_inputs` | `artifact_id`, `claim_id`, `relationship_id`, `source_revision_id` | Records authoritative inputs and permits rebuilds. |
| `import_runs` | `id`, `connector`, `started_at`, `finished_at`, `importer_version`, `status`, `receipt_json` | Detailed, idempotent import receipt. |
| `import_observations` | `id`, `import_run_id`, `source_document_id`, `source_revision_id`, `classification`, `outcome`, `warning_json` | Supports quarantine, move candidates, and deletion review without canonical deletion. |
| `import_candidates` | `id`, `source_document_id`, `fingerprint`, assertion/state/authority/visibility fields, `status`, `review_status`, `extractor_version`, `first_seen_import_run_id` | Source lifecycle and human review disposition are separate; candidates remain non-canonical until scoped application. |
| `import_candidate_evidence` | `candidate_id`, `source_revision_id`, `section_path`, offsets | Links retained candidates to every supporting immutable revision without duplication. |
| `candidate_dispositions` | `id`, `candidate_id`, `disposition`, `reason`, `created_at` | Immutable reject/defer history; no foreign-key path authorizes canonical mutation. |

The Markdown import operation writes source evidence, candidates, review items, observations, and its receipt in one Campaign Core transaction. It has no path to `entities`, `claims`, or `relationships`. Promoting a reviewed candidate requires the separately versioned `apply_change_set` operation.

The import-review read model queries these tables through Campaign Core only. Candidate detail slices the stored immutable UTF-8 revision using the recorded evidence offsets and returns that exact excerpt with path, section, classification, and hash. Receipt and review-item resources require DM visibility; candidate queries apply requester visibility in SQL. Pagination order is stable, and no read endpoint updates `review_items`, `import_candidates`, or canonical tables.

When `apply_change_set` commits, a transaction-bound trigger reconciles linked candidates only after all items for that candidate in the reviewed version have been applied. Multiple explicitly scoped approvals may complete one version without promoting siblings early. The same trigger closes the proposal only when every version item has an applied change-set item.

## Migration and rollback

Each migration is forward-only, transactional, and records its version in `campaign_schema_migrations`. Destructive column or enum changes use expand/backfill/contract migrations: first add compatible structures, backfill in a separately resumable job, deploy readers/writers that understand both forms, then remove the old form in a later release. Rollback before a destructive contract is the previous application plus its compatible schema; after one, restore the last tested logical PostgreSQL backup into a new database and cut over only after validation. Campaign truth is never rolled back by deleting source evidence or receipts.
